# Plan 5: Mirante evolving skills (repeated instructions become reviewed, signed, per-client skills)

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to work through this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Only one committing agent runs at a time (Plan 2b lesson). Read-only reviewers may run in parallel.

**Goal:** Stop the operator from typing the same instructions into every task.
- Mirante keeps a library of **skills**: reusable instructions plus optional reference files. It gives each new Claude Code or Codex session the skills whose **scope matches the task repo's normalized git origin**, in each tool's native form, and never edits `~/.claude` or `~/.codex`.
- Skills **evolve**. Mirante finds instructions the operator repeated across tasks (goals, steers, queued messages, denied permissions) and **proposes** a new skill or an edit to an existing one. Agents may propose too, through MCP.
- A person reviews every proposal, as with DNA. Every accepted version is **linted**, written as an immutable version folder with a **content-hash manifest**, **signed**, and checked again before each injection.

**Architecture:**
- **Source of truth: a user-level library, not the repo.**
  - Versions live at `$MIRANTE_HOME/skills/<name>/v<N>/`: `SKILL.md`, optional text files, `mirante-skill.json` (the manifest) and `mirante-skill.sig`.
  - Version folders are create-only: an edit is a new version, and the old ones stay for diff and rollback.
  - SQLite holds the index (current version, scope, status), the **trust ledger** of manifest hashes a person accepted, the proposal queue, tenants with learning enabled, and usage.
  - Client skills never enter client repos.
- **Tenant = normalized origin.**
  - Each task gets its origin key **at `task.create`, before an agent runs**. An agent that later rewrites `.git/config` cannot move the task into another client's tenant.
  - Scopes are `repo:<host>/<path>`, `org:<host>/<owner>[/…]` (path-segment prefix) and `personal`.
- **Pure core.** `mirante-core::skills` holds origin normalization, the format, lint, signing, the library and the miner. All of it can be tested without the daemon.
- **Injection per session.**
  - The hub resolves the matching skills and verifies each one: ledger hash, manifest hash, exact file list, file hashes, signature.
  - It hands **verified bytes** to the driver factory, which writes them under `<session_dir>/skills/<session_id>/`.
  - **Claude** gets a generated plugin (`--plugin-dir`) for on-demand skills, and `--append-system-prompt-file` for always-on skills.
  - **Codex** gets one extra text input item on the first turn of a new thread: always-on text plus an index of on-demand `SKILL.md` paths.
- **Evolving loop.**
  - Mining is opt-in per tenant and fully deterministic: redact, split into sentences, tokenize, Jaccard clusters, at least 3 distinct tasks in 60 days, never across tenants.
  - It drafts a proposal with no LLM involved.
  - **Refine with agent** queues an operator message to a task **of the same tenant**, and the agent answers through MCP `skill_propose`.
  - Agents never approve. The `Caller`/`identify`/`require_person` guard is reused unchanged.

**Tech Stack:**
- Rust 2021 (std threads), rusqlite 0.41 bundled, `sha2 0.10`, `libc`. No new crates.
- Signatures use OpenSSH SSHSIG (`ssh-keygen -Y`, namespace `mirante-skill`, ed25519 key generated by Mirante). It is the same format as git's ssh signing, so P7 can verify with an `allowed_signers` list.
- MCP: the existing `mirante-mcp` binary, serving a second surface under a separate server name, `mirante-skills`.
- Frontend: React 19 + Vitest. The line diff is a small LCS in TS; no new npm dependency.
- No embeddings, no API keys, no network. Replay or evals are out of scope (see Decision 12).

### Decisions this plan makes (and why)

1. **The library is user-level (`$MIRANTE_HOME/skills`), not `<repo>/.mirante/skills`.**
   - You work for several clients. A personal or org skill must not be committed into a client repo, and must not depend on one.
   - Repo-committed team skills wait for P7, the registry (open question 3).
   - `Paths` gains `skills()` (`<home>/skills`, 0700) and `keys()` (`<home>/keys`, 0700).
2. **Versions are immutable folders.**
   - Accepting a proposal creates `v<N+1>/`, written into a staging folder through `SafeDir`, then `renameat` to `v<N+1>` (fails if it exists).
   - SQL `skills.current_version` and `manifest_hash` point to it. Nothing is overwritten, so there is no expect-hash race on files.
   - Old versions stay for diff and rollback, keeping the newest 20; older ones are removed through the descriptor.
3. **Origin normalization (`skills::origin`).**
   - **Input.** Read raw with hardened `Git::checkout(repo).args(["config","--no-includes","--get","remote.origin.url"])`. Use `config --get`, never `remote get-url`: `insteadOf` is repo config an agent can plant.
   - **Accepted forms:** scp-like (`user@host:path`), `ssh://user@host[:port]/path`, `https://user:token@host[:port]/path` (userinfo dropped, never stored), `git://`.
   - **Path cleanup:** percent-decoded (`%20` becomes a space), trailing `.git` and `/` removed. Each segment is lowercased and checked (no empty segment, no `.` or `..`, no control characters).
   - **Host:**
     1. An exact `Host` alias from `~/.ssh/config` is mapped to its `HostName`. Literal patterns only: no wildcards, no `Match`, no `Include`, never `ssh -G`.
     2. Otherwise `<forge>-<suffix>` with forge in {`github.com`, `gitlab.com`, `bitbucket.org`} becomes the forge.
     3. The host is lowercased.
   - **Azure DevOps:** `ssh.dev.azure.com:v3/o/p/r`, `o@vs-ssh.visualstudio.com:v3/o/p/r`, `https://dev.azure.com/o/p/_git/r` and `https://o.visualstudio.com/p/_git/r` all become `dev.azure.com/o/p/r`.
   - **No origin, or a `file://` or local path:** `local/<sha256(canonical repo path)[..16]>`, which only `repo` and `personal` scopes match.
   - **Tenant (the mining boundary)** = host + first path segment (Azure: `dev.azure.com/<org>`).
4. **Scope matching.**
   - `repo:K` matches exactly K.
   - `org:P` matches when P's segments are a prefix of K's (at least host + 1 segment).
   - `personal` matches everything.
   - Scope lives inside the **signed manifest**, so widening it on disk breaks the signature. Rescoping is a person action that creates a new version.
   - Defaults:
     - Mined proposals: `repo` when all evidence is from one repo, else `org:<tenant>`.
     - Agent proposals: `repo` of the task.
     - Never `personal` unless a person picks it. The review card then warns "learned in <tenant>; personal skills reach every repo, including other clients'".
5. **The format is SKILL.md as both CLIs read it.**
   - Mirante **renders** `SKILL.md` itself: frontmatter `name` + `description` only (accepted by both Claude and Codex), then the body.
   - Imported frontmatter keys other than name and description are dropped with a lint warning. `allowed-tools` and `hooks` are lint **errors**, because they grant Claude permissions.
   - Names: `^[a-z0-9][a-z0-9-]{0,63}$`, without `claude` or `anthropic`.
   - Limits: description ≤1024 chars with no `<` or `>`; body ≤16 KiB; ≤8 extra files, text only (`.md`, `.txt`), not executable, ≤64 KiB each; ≤128 KiB per skill. Scripts are deferred.
6. **Manifest (`mirante-skill.json`, format `mirante.skill/v1`):**
   - Contents:

     ```json
     {"format":"mirante.skill/v1","name":"cargo-tests-first","version":3,
      "description":"…","activation":"always","agents":["claude","codex"],
      "scope":{"kind":"org","value":"github.com/sirus-alpha-canis"},
      "files":[{"path":"SKILL.md","sha256":"…","bytes":812}],
      "parent":"<sha256 of v2's manifest>|null",
      "provenance":{"source":"miner|agent|cli|import","task":null,"proposal":"…"},
      "signer":{"principal":"mirante-local","key":"SHA256:…"},
      "created":"2026-11-08"}
     ```

   - Serialization is canonical: serde struct order, compact, a trailing `\n`. `manifest_hash = sha256(bytes)`.
   - `mirante-skill.sig` is an armored SSHSIG over exactly those bytes.
   - **P7 hooks:** `format` is versioned; `signer.principal` names a key in an `allowed_signers` file; a version folder is a self-contained package (tar it to publish); `parent` chains versions.
7. **Signing.**
   - `trait Signer { fn sign(&self, msg: &[u8]) -> Result<String> }` and `trait Verifier { fn verify(&self, msg: &[u8], sig: &str, principal: &str) -> Result<()> }`. The only implementation is `SshKeygen`.
   - **Binary:** `/usr/bin/ssh-keygen`, overridable with `MIRANTE_SSH_KEYGEN`, never looked up on `PATH`.
   - **Environment:** `env_clear()` plus `PATH=/usr/bin:/bin`; no `SSH_AUTH_SOCK`; stdin is piped, so there is no tty.
   - **Commands:**
     - Sign: `-Y sign -n mirante-skill -f <key>` (message on stdin, signature on stdout).
     - Verify: `-Y verify -f <allowed_signers> -I mirante-local -n mirante-skill -s <tmp sig>`, message on stdin. The signature is copied 0600 into `<home>/tmp/` from bytes read through `SafeDir`.
   - The key is generated on first accept (`ssh-keygen -q -t ed25519 -N "" -C mirante-skills -f <home>/keys/skills_ed25519`). `allowed_signers` holds `mirante-local namespaces="mirante-skill" <pub>`.
   - No `ssh-keygen` means no injection: a `skill.unavailable` event says why.
   - The signature does not stop an agent with shell access that reads the key (same uid; see Risks). It catches edits made outside Mirante and gives P7 portable provenance. **Injection requires both the ledger and the signature.**
8. **Native injection, per session, never global.**
   - **Claude, on-demand skills:** `<sess>/claude-plugin/.claude-plugin/plugin.json` (`{"name":"mirante-skills","version":"0.0.0","description":"Skills Mirante injected for this task"}`) and `skills/<name>/SKILL.md` (+ files). Passed as `--plugin-dir <dir>`. Invoked as `mirante-skills:<name>`.
   - **Claude, always-on skills:** `<sess>/always.md` passed as `--append-system-prompt-file`.
   - **Claude fallback:** if Task 12's live check finds the hidden flag refused, pass `--append-system-prompt <text>` instead, inline, capped at 8 KiB.
   - **Codex:** an extra input item before the goal on the first `turn/start` of a **new** thread (never on resume, where it is already in history). It holds a `<mirante-skills>` block with the always-on text and the index of on-demand skills (`name — description — read <abs path>/SKILL.md when relevant`).
   - **Budget:** at most 24 skills and 8 KiB of always-on text per session. Narrower scopes win (repo, then org, then personal), then most recently updated. Anything over the budget is skipped with `skill.refused {reason:"over budget"}`.
   - Skills apply to **new** sessions. On a Claude resume, the plugin is rebuilt but the system-prompt snapshot keeps the old always-on text until compaction (documented).
9. **Mining (`skills::mine`).**
   - **Sources** (Mirante's own SQLite only):
     - `tasks.goal`;
     - `events` of kind `message_sent` and `message_queued` (`text`);
     - `permission_requests` with status `denied` (tool + detail). Denials only: allows are never mined, so nothing pushes toward auto-approval.
   - **Filters:** texts starting with `Operator request:` (Mirante's own templates) are skipped. Window: 60 days. **Tenants with learning enabled only** (opt-in, default off).
   - **Units:** redact, then split on lines, `. `, `; ` and `? `; strip bullets; keep 4 to 60 tokens.
   - **Tokens:** lowercased, accent-folded (reuse the `slugify` table, since your messages are Portuguese and English), split on non-alphanumerics, small EN+PT stopword list.
   - **Clustering:** greedy by time, joining a cluster when Jaccard ≥0.5 or containment ≥0.8. A cluster qualifies at ≥3 distinct tasks of one tenant.
   - **Draft:**
     - The representative is the medoid.
     - It is **covered** (skipped) when Jaccard ≥0.5 with any body line of an active in-scope skill.
     - If ≥2/3 of the cluster's tasks ran with skill X active, the result is an **edit** proposal that appends the line to X. Otherwise it is a **new** skill:
       - name `slugify(top 3 tokens)` with a `-2` suffix on collision;
       - description `Instructions the operator repeated in N tasks: <first 120 chars>`;
       - activation `always`.
   - **Fingerprint:** `sha256(tenant + sorted tokens)[..16]`. A pending proposal with the same fingerprint gets its evidence updated. A rejected fingerprint is never proposed again.
   - **Denials** cluster on `(tool, first two words of the redacted command)` and draft the line ``Do not run `<cmd>`; ask the operator first (denied in N tasks).``
   - **Triggers:** on demand (`skill.mine`, cockpit **Find repeated instructions**, `mirante skills mine`) and after `task.archive`. Nothing runs in the background.
10. **Proposals and review (the DNA pattern).**
    - **Origins:** `miner`, `agent` (MCP `skill_propose`, bound to the caller's own task like `dna.propose`), `cli` and `import` (a person, through `skill.add`).
    - **Edit proposals** pin `base_hash`. If the skill moved on since, Accept returns `CONFLICT` and the card shows the new diff.
    - **Person-only methods:** `skill.review`, `skill.action`, `skill.learn`, `skill.mine` and `skill.add` call `require_person`. Mirante-launched agents and unverified callers get `FORBIDDEN` with the DNA message adapted ("reviewing skills is a person's decision").
    - **Accept:** re-redact and re-lint the edited text (any lint **error** refuses), render, write the version, sign, then write the ledger + index + `skill.decided` in one transaction. If the store refuses, the staged folder is removed.
11. **Untrusted text.**
    - Proposal text from agents is data until accepted. The cockpit renders it as text nodes; the CLI prints it through `untrusted::line`.
    - The miner's evidence examples are the operator's own words, redacted.
    - Accepted skills are injected **as instructions** (that is their purpose). That is why lint runs on every accept, and why a skill changed on disk is never injected until a person re-adopts it (`skill.add` from its folder, which goes through review).
12. **YAGNI, deferred:**
    - replay or held-out evaluation (SkillOpt's acceptance test, concept only; `claude plugin eval` exists for later);
    - repo-committed team skills;
    - scripts in skills;
    - Codex native skill registration (try `-c skills.config` in Task 13's live check and record the result only);
    - per-skill usage for Codex beyond "injected".

### Lint rules (`skills::lint`, deterministic)

| Rule | Severity | Examples |
|---|---|---|
| `size` | error | body >16 KiB, description >1024, >8 files, file >64 KiB |
| `name` | error | not `^[a-z0-9][a-z0-9-]{0,63}$`, contains `claude` or `anthropic` |
| `secret` | error | `redact_counted(text).1 > 0` |
| `invisible` | error | any character `untrusted::line` would strip (C0/C1, bidi, zero-width, tag characters) |
| `forbidden` | error | `dangerously-skip-permissions`, `bypassPermissions`, `--yolo`, `approval_policy`/`approvalPolicy` `never`, `danger-full-access`, `auto-approve`, `always allow`, `don't/do not ask (for) permission`, `skip hooks`, `--no-verify`, `disable the sandbox`, frontmatter `allowed-tools` / `hooks` |
| `shell` | error | `rm -rf /`, `rm -rf ~`, `curl … \| sh`, `wget … \| bash`, `base64 -d \| sh`, `chmod 777`, `sudo `, writes into `~/.ssh`, `~/.aws`, `~/.claude`, `~/.codex` or `~/.mirante` |
| `injection` | error | `ignore (all) previous/prior instructions`, `you are now`, `system prompt`, `<|im_start\|>`, `</mirante-`, `<mirante-skills` |
| `refs` | error / warn | a relative link or backticked path to a missing bundled file (error); an absolute or `..` path (error); a user home path `/Users/…` (warn) |
| `comment` | warn | `<!--` hidden text |

Matching runs on a folded copy (ASCII lowercase, fullwidth ASCII to ASCII, whitespace runs collapsed). Findings carry `{rule, severity, line, message}`.

## Risks

- **Same-uid key.** An agent with shell access (after the user allows it) can read `~/.mirante/keys` and the SQLite ledger, sign a planted version and insert a row. The signature and ledger detect edits made **outside** Mirante, not a determined same-uid attacker. This is the same boundary as Plan 4's Risks; the real fix (a per-connection capability, keys in the Keychain) is out of scope.
